# СЕРТИФИКАТЫ (нейрополя)

## Основы управления

### 1. Система управления сертификатами

В ОС Альт управление доверенными корневыми сертификатами осуществляется с помощью пакета `ca-trust`, который включает утилиту `update-ca-trust`.

Для проверки наличия пакетов в репозитории используется команда (выполняется без привилегий):

```bash
$ apt-cache search ca-trust
```

Ожидаемый вывод содержит строки:
- `ca-trust` – основной пакет инфраструктуры доверия;
- `ca-trust-directory-hash` – хук для создания каталога с хеш‑ссылками;
- `ca-trust-java` – хук для интеграции с Java.

Установка пакета (при необходимости) выполняется от имени суперпользователя:

```bash
apt-get install ca-trust
```

Система сертификатов в ОС Альт соответствует модели Red Hat Enterprise Linux (RHEL) и использует каталоги `/etc/pki/ca-trust/` и `/etc/pki/tls/certs/`.

### 2. Расположение системных файлов сертификатов

| Назначение | Путь |
|------------|------|
| Каталог для размещения пользовательских корневых сертификатов | `/etc/pki/ca-trust/source/anchors/` |
| Альтернативный каталог для корневых сертификатов | `/usr/share/pki/ca-trust-source/anchors/` |
| Основной файл со всеми доверенными сертификатами (в формате PEM) | `/etc/pki/tls/certs/ca-bundle.crt` |
| Файл сертификатов с атрибутами доверия | `/etc/pki/tls/certs/ca-bundle.trust.crt` |
| Извлечённые сертификаты для OpenSSL | `/etc/pki/ca-trust/extracted/pem/` |

Все команды модификации файлов в указанных каталогах требуют прав суперпользователя.

### 3. Добавление пользовательских корневых сертификатов

Для добавления собственного корневого сертификата в системное хранилище необходимо выполнить следующие действия (все команды выполняются от root):

1. Поместить файл сертификата в формате PEM (с расширением `.crt`) в каталог:
```bash
cp my_cert.crt /etc/pki/ca-trust/source/anchors/
```

2. Обновить системное хранилище сертификатов:
```bash
update-ca-trust
```
или
```bash
update-ca-trust extract
```

После выполнения этих команд все сертификаты из каталога `anchors/` будут объединены в файлы `ca-bundle.crt` и `ca-bundle.trust.crt`.

### 4. Просмотр установленных сертификатов

#### 4.1. Просмотр с помощью утилиты `trust` (рекомендованный способ)

Для просмотра списка всех доверенных сертификатов:

```bash
$ trust list
```

Для получения подробной информации по каждому сертификату:

```bash
$ trust list --detail
```

#### 4.2. Просмотр содержимого файла `ca-bundle.crt`

Просмотр всего файла (очень большой объём вывода):

```bash
$ cat /etc/pki/tls/certs/ca-bundle.crt
```

Подсчёт количества сертификатов в хранилище:

```bash
$ grep -c "BEGIN CERTIFICATE" /etc/pki/tls/certs/ca-bundle.crt
```

#### 4.3. Просмотр с помощью OpenSSL

Вывод информации о первом сертификате в файле (команда обрабатывает только один сертификат):

```bash
$ openssl x509 -in /etc/pki/tls/certs/ca-bundle.crt -noout -subject -issuer
```

Для просмотра всех сертификатов с полной информацией используйте конвейер:

```bash
$ openssl crl2pkcs7 -nocrl -certfile /etc/pki/tls/certs/ca-bundle.crt | openssl pkcs7 -print_certs -noout -text
```

Для вывода только полей `subject` и `issuer` для всех сертификатов:

```bash
$ openssl crl2pkcs7 -nocrl -certfile /etc/pki/tls/certs/ca-bundle.crt | openssl pkcs7 -print_certs -noout -text | grep -E "subject:|issuer:"
```

### 5. Просмотр сертификатов в специализированных хранилищах

#### 5.1. Хранилище NSS (для браузеров Firefox, Chromium)

Для работы с хранилищем NSS необходимо установить пакет `nss-tools`:

```bash
apt-get install nss-tools
```

Просмотр сертификатов в пользовательском хранилище NSS:

```bash
$ certutil -d sql:$HOME/.pki/nssdb -L
```

Если хранилище не инициализировано, команда может вернуть ошибку.

#### 5.2. Хранилище Java

Для просмотра системного хранилища Java `cacerts` используется утилита `keytool`. Рекомендуется использовать опцию `-cacerts`, которая автоматически указывает на системное хранилище:

```bash
$ keytool -list -cacerts
```

При запросе пароля введите `changeit` (стандартный пароль для `cacerts`, если он не был изменён администратором). Также можно указать пароль непосредственно в команде (небезопасно, так как пароль будет виден в истории команд):

```bash
$ keytool -list -keystore /etc/pki/java/cacerts -storepass changeit
```

Для просмотра хранилища, отличного от системного, укажите путь к файлу `cacerts`:

```bash
$ keytool -list -keystore /path/to/cacerts
```

### 6. Удаление сертификатов

Для удаления ранее добавленного сертификата необходимо (от root):

1. Удалить соответствующий файл из каталога `/etc/pki/ca-trust/source/anchors/`:
```bash
rm /etc/pki/ca-trust/source/anchors/my_cert.crt
```

2. Обновить системное хранилище:
```bash
update-ca-trust
```

### 7. Примечания

- Для корректной работы сертификатов они должны быть в формате PEM (X.509) с начальной строкой `-----BEGIN CERTIFICATE-----`.
- В ОС Альт присутствует собственный корневой центр сертификации: `ALT Root Certification`.
- В некоторых конфигурациях может присутствовать символическая ссылка `/etc/ssl/certs/ca-certificates.crt` на `/etc/pki/tls/certs/ca-bundle.trust.crt`.
- Для работы с российскими сертификатами может потребоваться установка пакета `ca-certificates`, содержащего сертификаты общедоступных центров сертификации.
- Все команды, изменяющие системные файлы, требуют прав суперпользователя. Для переключения в режим root используйте `su -` (если известен пароль) или `sudo`, если он настроен. В руководстве команды, требующие прав root, помечены символом `#`, команды, выполняемые от имени обычного пользователя, – символом `$`.



## Сетевая PKI

Для построения сети из трёх равноправных (перекрёстно сертифицированных) Удостоверяющих Центров (УЦ) используется механизм **перекрёстного подписания (cross-certification)**. В такой схеме каждый УЦ является корневым (самоподписанным) и одновременно доверяет двум другим, подписывая их сертификаты.

### 1. Подготовка структуры каталогов

Создайте отдельные директории для каждого УЦ и общую директорию для обмена запросами:

```bash
mkdir -p CA1 CA2 CA3 csr
```

### 2. Генерация корневых сертификатов для каждого УЦ

Каждый УЦ создаёт свою самоподписанную корневую пару (ключ + сертификат).

#### УЦ-1
```bash
# Генерация закрытого ключа
openssl genrsa -out CA1/ca1.key 4096

# Создание самоподписанного корневого сертификата (сроком на 10 лет)
openssl req -x509 -new -nodes -key CA1/ca1.key -sha256 -days 3650 \
  -out CA1/ca1.crt \
  -subj "/C=RU/ST=Moscow/L=Moscow/O=CA1/CN=Root CA1"
```

#### УЦ-2
```bash
openssl genrsa -out CA2/ca2.key 4096
openssl req -x509 -new -nodes -key CA2/ca2.key -sha256 -days 3650 \
  -out CA2/ca2.crt \
  -subj "/C=RU/ST=Moscow/L=Moscow/O=CA2/CN=Root CA2"
```

#### УЦ-3
```bash
openssl genrsa -out CA3/ca3.key 4096
openssl req -x509 -new -nodes -key CA3/ca3.key -sha256 -days 3650 \
  -out CA3/ca3.crt \
  -subj "/C=RU/ST=Moscow/L=Moscow/O=CA3/CN=Root CA3"
```

### 3. Подготовка запросов на сертификацию (CSR) для перекрёстного подписания

Каждый УЦ генерирует запрос на основе своего **уже существующего** корневого ключа (без создания нового). Этот запрос будет отправлен другому УЦ для подписания.

#### Для УЦ-1 (запрос на подпись у УЦ-2 и УЦ-3)
```bash
openssl req -new -key CA1/ca1.key -out csr/ca1_cross.csr \
  -subj "/C=RU/ST=Moscow/L=Moscow/O=CA1/CN=Root CA1"
```

#### Для УЦ-2
```bash
openssl req -new -key CA2/ca2.key -out csr/ca2_cross.csr \
  -subj "/C=RU/ST=Moscow/L=Moscow/O=CA2/CN=Root CA2"
```

#### Для УЦ-3
```bash
openssl req -new -key CA3/ca3.key -out csr/ca3_cross.csr \
  -subj "/C=RU/ST=Moscow/L=Moscow/O=CA3/CN=Root CA3"
```

### 4. Перекрёстное подписание сертификатов

Теперь каждый УЦ подписывает запросы двух других УЦ, создавая для них перекрёстные сертификаты. Для этого используется расширение `v3_ca`, чтобы сертификат мог выступать в роли УЦ.

#### УЦ-1 подписывает УЦ-2 и УЦ-3
```bash
# Подпись сертификата УЦ-2
openssl x509 -req -in csr/ca2_cross.csr -CA CA1/ca1.crt -CAkey CA1/ca1.key \
  -CAcreateserial -out CA2/ca1-cross-ca2.crt -days 1825 -sha256 -extensions v3_ca

# Подпись сертификата УЦ-3
openssl x509 -req -in csr/ca3_cross.csr -CA CA1/ca1.crt -CAkey CA1/ca1.key \
  -CAcreateserial -out CA3/ca1-cross-ca3.crt -days 1825 -sha256 -extensions v3_ca
```

#### УЦ-2 подписывает УЦ-1 и УЦ-3
```bash
openssl x509 -req -in csr/ca1_cross.csr -CA CA2/ca2.crt -CAkey CA2/ca2.key \
  -CAcreateserial -out CA1/ca2-cross-ca1.crt -days 1825 -sha256 -extensions v3_ca

openssl x509 -req -in csr/ca3_cross.csr -CA CA2/ca2.crt -CAkey CA2/ca2.key \
  -CAcreateserial -out CA3/ca2-cross-ca3.crt -days 1825 -sha256 -extensions v3_ca
```

#### УЦ-3 подписывает УЦ-1 и УЦ-2
```bash
openssl x509 -req -in csr/ca1_cross.csr -CA CA3/ca3.crt -CAkey CA3/ca3.key \
  -CAcreateserial -out CA1/ca3-cross-ca1.crt -days 1825 -sha256 -extensions v3_ca

openssl x509 -req -in csr/ca2_cross.csr -CA CA3/ca3.crt -CAkey CA3/ca3.key \
  -CAcreateserial -out CA2/ca3-cross-ca2.crt -days 1825 -sha256 -extensions v3_ca
```

### 5. Итоговая структура

После выполнения всех команд каждый УЦ будет иметь в своей директории:
- Свой корневой сертификат (`caN.crt`) и ключ (`caN.key`).
- Два перекрёстных сертификата от двух других УЦ.

Например, в директории `CA1`:
- `ca1.crt` — самоподписанный корневой сертификат УЦ-1.
- `ca2-cross-ca1.crt` — сертификат УЦ-1, подписанный УЦ-2.
- `ca3-cross-ca1.crt` — сертификат УЦ-1, подписанный УЦ-3.

### 6. Проверка корректности

Чтобы убедиться, что перекрёстная сертификация выполнена верно, можно проверить сертификат УЦ-1, подписанный УЦ-2:

```bash
openssl verify -CAfile CA2/ca2.crt CA1/ca2-cross-ca1.crt
```

Ожидаемый вывод: `CA1/ca2-cross-ca1.crt: OK`

### Важные замечания

1. **Единое Subject**: При перекрёстном подписании важно, чтобы во всех запросах (`CSR`) и корневых сертификатах **полностью совпадало** поле Subject (в примере это `"/C=RU/ST=Moscow/L=Moscow/O=CA1/CN=Root CA1"`). Иначе цепочка доверия не будет построена корректно.

2. **Срок действия**: Срок перекрёстных сертификатов (в примере — 5 лет) не должен превышать срок действия корневого сертификата (10 лет).

3. **Расширения**: Использование `-extensions v3_ca` при подписании гарантирует, что сертификат будет содержать расширение `basicConstraints=CA:TRUE`, что обязательно для УЦ.

4. **Файл серийных номеров**: Параметр `-CAcreateserial` автоматически создаёт файл с серийным номером. При повторных запусках лучше использовать `-CAserial serial.txt` для контроля уникальности серийных номеров.

Эта схема позволяет любому из трёх УЦ выпускать сертификаты для конечных пользователей, которые будут приниматься всеми участниками сети, так как каждый УЦ доверяет двум другим через цепочки перекрёстных сертификатов.


## Сертификат для IP-адреса

Чтобы выдать сертификат для IP-адреса, нужно обязательно указать его в расширении **Subject Alternative Name (SAN)**. Современные браузеры и программы игнорируют поле `Common Name (CN)` для проверки IP-адресов и требуют именно SAN.

Вот два основных способа, как это сделать с помощью OpenSSL.

### Способ 1: Одна команда (самый простой)

Этот способ подходит для OpenSSL версии 1.1.1 и выше. Вы создаете самоподписанный сертификат одной командой, используя параметр `-addext`.

Замените `192.168.1.100` на ваш IP-адрес:

```bash
openssl req -x509 -newkey rsa:2048 -nodes -keyout server.key -out server.crt -days 365 -subj "/CN=192.168.1.100" -addext "subjectAltName = IP:192.168.1.100"
```

**Пояснение параметров**:
*   `req -x509`: создает самоподписанный сертификат (а не запрос на подпись).
*   `-newkey rsa:2048`: генерирует новый 2048-битный RSA-ключ.
*   `-nodes`: не шифровать приватный ключ паролем.
*   `-keyout server.key`: файл для сохранения приватного ключа.
*   `-out server.crt`: файл для сохранения сертификата.
*   `-days 365`: срок действия сертификата (в днях).
*   `-subj "/CN=192.168.1.100"`: задает Common Name (обычно его тоже указывают как IP).
*   `-addext "subjectAltName = IP:192.168.1.100"`: **самая важная часть** — добавляет IP-адрес в расширение SAN.

### Способ 2: С использованием файла конфигурации

Этот способ дает больше контроля, особенно если нужно указать несколько IP-адресов или доменов.

**Шаг 1: Создайте файл конфигурации `openssl.cnf`**

```ini
[req]
# Секция [req] — обязательная для команды openssl req. Она задаёт параметры запроса на сертификат.
distinguished_name = req_distinguished_name
# Указывает, в какой секции находятся поля Distinguished Name (DN) — идентификационные данные владельца.
req_extensions = v3_req
# Указывает, в какой секции определены расширения (extensions) для запроса (v3).

[req_distinguished_name]
# Секция, в которой перечислены поля DN, запрашиваемые при создании CSR.
# Здесь мы определяем только Common Name, остальные поля (страна, город и т.д.) не запрашиваются.
commonName = Common Name (e.g., server FQDN or YOUR name)
# Это описание поля commonName — оно будет отображаться как подсказка при интерактивном вводе.
commonName_default = 192.168.1.100
# Значение по умолчанию для commonName — автоматически подставляется, если не вводить вручную.
# Указываем IP-адрес, чтобы CN тоже содержал IP (хотя браузеры смотрят на SAN, но для совместимости оставляем).

[v3_req]
# Секция с расширениями версии 3 (v3), которые будут включены в запрос и затем в сертификат.
keyUsage = keyEncipherment, dataEncipherment
# Определяет назначение ключа: keyEncipherment — для шифрования симметричных ключей при обмене,
# dataEncipherment — для шифрования данных напрямую (обычно для серверных сертификатов достаточно первого).
extendedKeyUsage = serverAuth
# Расширенное использование ключа: serverAuth — сертификат может использоваться для аутентификации сервера (TLS/SSL).
subjectAltName = @alt_names
# Указывает, что Subject Alternative Name (SAN) берётся из секции с именем alt_names.
# Это критично для IP-адресов — именно здесь браузер будет проверять адрес.

[alt_names]
# Секция, где перечисляются альтернативные имена (SAN) — все адреса, для которых сертификат действителен.
# Здесь указываются IP-адреса и/или DNS-имена.
IP.1 = 192.168.1.100
# Первый IP-адрес в списке SAN. Именно его будет проверять браузер при подключении по IP.
# Если вы хотите добавить ещё IP, нумеруйте их последовательно: IP.2, IP.3 и т.д.
# IP.2 = 10.0.0.2
# (закомментировано) Пример добавления второго IP-адреса.
# DNS.1 = my-server.local
# (закомментировано) Пример добавления доменного имени (если нужно, чтобы сертификат работал и для DNS-имён).
```
Этот пример конфигурации взят из статьи на Cloud.tencent.com.

**Шаг 2: Сгенерируйте приватный ключ**
```bash
openssl genrsa -out server.key 2048
```


**Шаг 3: Создайте запрос на подпись сертификата (CSR)**
```bash
openssl req -new -out server.csr -key server.key -config openssl.cnf
```


**Шаг 4: Подпишите сертификат самостоятельно**
```bash
openssl x509 -req -in server.csr -signkey server.key -out server.crt -days 365 -extensions v3_req -extfile openssl.cnf
```


### Важные моменты

*   **Поле Common Name (CN)**: Хотя его и указывают, для корректной работы оно не является обязательным. Главное — это расширение `subjectAltName`.
*   **Несколько IP-адресов**: В расширении `subjectAltName` можно перечислить несколько адресов, пронумеровав их (`IP.1`, `IP.2` и т.д.).
